# Contributing

Спасибо за интерес к проекту! Здесь — как поднять окружение, прогнать тесты и оформить PR.

## Ветки и PR

Модель — trunk-based: `main` единственная долгоживущая ветка, всегда в состоянии
«можно ставить пользователям» (HACS отдаёт пользователям не каждый коммит `main`,
а только то, что явно затегировано — так что `main` может свободно содержать
смерженные, но ещё не выпущенные изменения).

- Работайте в короткоживущей ветке от `main`, называйте по смыслу изменения:
  `fix/...`, `feat/...`, `ci/...`, `docs/...`, `chore/...`.
- Один PR — одно независимо проверяемое и независимо откатываемое изменение.
  Не смешивайте в одном PR несвязанные правки (например, багфикс и рефакторинг
  стиля) — так проще ревьюить и, если что-то одно сломается, откатить только его.
- Прямой пуш в `main` закрыт — весь код идёт только через PR с зелёным CI.

## Окружение для разработки

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate

pip install ruff
pip install "pytest-homeassistant-custom-component==0.13.54" "homeassistant==2023.9.0"
```

Версии `pytest-homeassistant-custom-component`/`homeassistant` могут со временем
измениться — актуальный пин всегда смотрите в
[`.github/workflows/tests.yml`](.github/workflows/tests.yml), он тут не дублируется
намеренно, чтобы не разъезжаться с CI.

## Тесты

```bash
pytest tests/ --cov=custom_components.rosdomofon --cov-report=term-missing
```

CI дополнительно гоняет тесты и против последней версии Home Assistant
(`ha-version: latest` в матрице) — это информационная проверка (не блокирует
мердж), сигнализирует о поломках от будущих изменений API HA заранее.

## Линтинг

```bash
ruff check custom_components tests
```

Правила — в [`ruff.toml`](ruff.toml). Набор сознательно минимальный (Pyflakes +
часть pycodestyle) и расширяется постепенно, а не разом.

## Стиль кода

- Все URL и эндпоинты API Росдомофон — в `custom_components/rosdomofon/const.py`,
  не хардкодьте их по месту использования.
- Docstring'и и логи — на русском (сложившаяся конвенция проекта), имена
  переменных/функций — на английском.
- Коммит-сообщение: короткое императивное описание того, что сделано и зачем
  (не `update`/`fix` без контекста) — оно попадает в release notes при релизе
  (см. `.github/workflows/release.yml`).

## Версионирование и релизы

Версия — в `custom_components/rosdomofon/manifest.json`, семвер:

- **patch** — багфикс без изменения поведения;
- **minor** — новая функциональность, обратно совместимая;
- **major** — breaking change.

Если PR достаточно значим, чтобы стать релизом — бампните `version` в manifest.json
в этом же PR. Сам релиз (git-тег + GitHub Release) делает мейнтейнер отдельным
действием после мерджа: `git tag X.Y.Z && git push origin X.Y.Z` — тег должен
совпадать с `manifest.json.version`, иначе `release.yml` упадёт на проверке.

## Issues

Прежде чем открывать issue — проверьте, что похожей ещё нет. Для багов
используйте шаблон и приложите debug-лог интеграции (как включить — написано
в самом шаблоне) — без него разобраться в проблеме почти всегда сложнее, чем
кажется на первый взгляд.
